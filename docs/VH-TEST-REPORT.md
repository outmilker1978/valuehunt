# VH — Тестирование оценки вакансий: методология, результаты, архитектурные выводы

## 1. Цель тестирования

Проверить, **совпадают ли результаты оценки VH с ручной оценкой по UES** при анализе одних и тех же HH-вакансий. Если нет — найти корневые причины и предложить архитектурные решения без хардкода.

**Принцип:** продукт должен быть универсальным. Личная матрица ценностей пользователя — только пример конфигурации. Любой другой пользователь с другой матрицей должен получить адекватные оценки без правки кода.

## 4. Исследование корневых причин

### 4.1 Архитектурная проблема: две несвязанные системы

В VH существуют **два независимых механизма оценки**, которые не связаны друг с другом:

```
matrix.yaml                          UESCalculator (ues.py)
┌─────────────────────────┐         ┌──────────────────────────┐
│ 7 групп, 28 критериев   │         │ 3 группы (хардкод)       │
│ keywords, weights,      │         │ kw_map (хардкод,         │
│ alternatives            │         │   строка 268-324)        │
│                         │         │                          │
│ Используется:           │         │ Используется:            │
│ web UI (матрица)        │         │ scanner → оценивание     │
│ ТОЛЬКО для отображения  │         │ ВСЕХ вакансий            │
└─────────┬───────────────┘         └──────────┬───────────────┘
          │ НЕ ПЕРЕДАЁТСЯ                       │ ХАРДКОД
          ▼                                     ▼
    Редактирование матрицы           Оценка не меняется
    в UI не влияет на оценки
```

**Факт:** `matrix.yaml` загружается в `app.py:166-171()` только для отображения в веб-интерфейсе. UESCalculator в `ues.py` имеет собственный жёстко зашитый `kw_map` (строки 268-324). Изменение matrix.yaml **никак не влияет** на результаты оценки.

### 4.2 Отсутствие механизма блокирующих критериев

Все критерии в VH работают **только в плюс**: нашли ключевое слово → добавили баллы. Нет механизма:

- **«Если найдено → REJECT»** (например: gambling, igaming, team lead, CPO)
- **«Если формат = офис → Gate A fail»** — Gate A проверяет текст на наличие "офис" без "удалёнка", но:
  - ECOS (офис) получил 7.63 → Gate A пропустил
  - Риверхаус (Team Lead) получил 7.38 → Gate B пропустил

### 4.3 Статистика оценки критериев

Текущий `kw_map` в `_rate_criterion()` содержит **45 ключевых слов** (по всем критериям). Для сверки — в `matrix.yaml` их **~230**. При этом matrix.yaml не участвует в скоринге.

### 4.4 Отсутствие проверки опыта (years of experience)

В `_check_gate_a()` нет проверки на соответствие опыта кандидата требованиям вакансии. Северсталь с требованием «1–3 года» получила 6.75 баллов — для Senior PM это должно быть автоматическим REJECT (overqualified).

### 4.5 Отсутствие проверки английского языка

В `DEFAULT_UES_CONFIG` и `matrix.yaml` нет ни одного критерия, связанного с английским. Вакансия evrone.ru (требование Upper Intermediate) получила 8.05 без учёта этого.

## 5. Выводы

1. **VH не проходит тест «одинаковый результат с ручной оценкой».** Из 10 проверенных вакансий только 3 совпали (все REJECT). Системное завышение: ~+2.9 балла.

2. **matrix.yaml — мёртвая конфигурация.** Она редактируется в UI, но не влияет на скоринг. Реальный движок оценки — хардкод в `ues.py:268-324`.

3. **Нет блокирующих критериев.** Экосистема оценивает «по совпадению» (позитивный скоринг), но не умеет «отбраковывать» по красным флагам.

4. **Gate A и Gate B — не параметризуемые.** Их логика (что считается удалёнкой, какие роли проходят) зашита в Python-методах. Изменение матрицы не меняет поведение Gate.

5. **Частично VH работает правильно** — весь явный мусор (строительство, не-IT, Казахстан) отсекается в REJECT. Проблемы начинаются на границе «похоже на PM, но не совсем».

## 6. Предложения: как должно работать

### 6.1 Принцип: единый источник правил

**matrix.yaml должен быть единственным источником правил для оценки.** UESCalculator читает YAML, а не хардкод.

```
matrix.yaml (7 групп, ~28 критериев, ~230 ключевых слов)
       ↓
UESCalculator (читает YAML вместо хардкода)
       ↓
scanner.py (оценивает по YAML-правилам)
       ↓
БД (результаты)
```

### 6.2 Что добавить в matrix.yaml

#### 6.2.1 Блокирующие критерии (red_flags / blockers)

Новая секция в корне YAML — критерии, которые при совпадении дают REJECT вне зависимости от баллов:

```yaml
blocks:
  # Стоп-факторы по домену (ценности)
  - id: ban_gambling
    name: Гемблинг/букмекерство
    mode: reject          # reject | warn (warn не блокирует, а подсвечивает)
    target: full_text     # full_text | title | skills
    keywords:
      - gambling, betting, casino, crypto, igaming, букмекер, winline, bitcoin mining
    
  - id: ban_non_pm_role
    name: Роль не PM/PO
    mode: reject
    target: title         # проверять только по названию
    keywords:
      - team lead, tech lead, engineering manager, chief product officer
      - cpo, head of engineering, data scientist, data engineer
    
  - id: ban_office_only
    name: Офис (не удалёнка)
    mode: reject
    target: full_text
    keywords:
      - на месте работодателя
      - работа строго в офисе
      - удаленный формат не рассматривается
    # Логика: если найдено хотя бы одно из этих И не найдено "удалёнка" → reject
```

#### 6.2.2 Расширение критериев: поле blocking/reject

Каждый существующий критерий может получить флаг блокировки:

```yaml
- id: conditions
  name: Условия работы
  weight: 10
  criteria:
    - id: remote_100
      name: Удалёнка 100%
      weight: 10
      blocking: true    # <-- если НЕ совпало → REJECT (Gate A fail)
      keywords:
        - удалённая работа, remote, дистанционно
    - id: office_moscow
      name: Офис Москва
      weight: 4
      blocking: true    # <-- если совпало без remote → REJECT
```

#### 6.2.3 Добавить критерии, которых не хватает

- **english_level** — минимальный уровень английского, параметризуется в profile.json
- **experience_years** — проверка: опыт кандидата vs требования вакансии. Если вакансия просит «1-3 года» → предупреждение/REJECT для Senior
- **domain** — зелёные домены (enterprise, healthcare, gov) и красные (gambling, betting)

### 6.3 Изменения в profile.json

Добавить конфигурацию для валидации блоков и Gate-проверок:

```json
{
  "profile": {
    "gates": {
      "mode": "strict",           // strict | lenient
      "blockers_enabled": true,   // включить блокирующие критерии
      "override_enabled": true     // High Potential Override
    },
    "experience_years": 20,       // для проверки overqualified
    "english_level": "A2-B1",     // минимальный приемлемый
    "salary_min": 250000,
    "work_format": "REMOTE"
  }
}
```

### 6.4 Как это меняет логику UESCalculator

**Сейчас (хардкод):**
```
1. Gate A — хардкодные проверки в _check_gate_a()
2. Gate B — хардкодные списки archetype_01, archetype_03
3. Score — kw_map в _rate_criterion() (45 слов)
4. Classify — пороги 8.0/7.0/6.0/5.0
```

**Должно быть:**
```
1. Load matrix.yaml → rules
2. Process blocks → reject if any block matched
3. Process gates (Gate A, Gate B) из конфига, не из кода
4. Score criteria → читать kw из YAML, не из kw_map
5. Classify → пороги из конфига, не хардкод
```

### 6.5 Режим «только Gate» для быстрого пре-фильтра

Для массового сканирования (100+ вакансий) нужен режим, который:
1. Проверяет только **blocks** (красные флаги)
2. Проверяет **Gate A + Gate B**
3. Отсеивает REJECT
4. Полный скоринг — только для прошедших

Это уже заложено в `gate_check.py`, но он сейчас дублирует код из `ues.py`, а не читает YAML.

### 6.6 Тест на воспроизводимость

После внедрения новая проверка: **10 тех же вакансий должны дать те же оценки, что и ручные**.

| Вакансия | Ожидание (manual) | Критерий приёмки |
|----------|:-----------------:|-------------------|
| ECOS Crypto | REJECT | blocks.ban_gambling → reject |
| Риверхаус Team Lead | REJECT | blocks.ban_non_pm_role → reject |
| Azur Games | REJECT | blocks.ban_non_pm_role → reject |
| Северсталь | ~4.5 (C) | overqualified → снижение балла |
| evrone.ru | ~6.5 (B) | english_level check → снижение |
| CyberOK | ~5.5 (C) | brand_stability → честная оценка |
| FIX | ~6.3 (B) | допустимо расхождение ±0.5 |
| Менеджед Деплоймент | ~5.8 (C) | допустимо расхождение ±0.5 |

## 7. Резюме для разработчика (кратко)

**Что сломано:**
- `matrix.yaml` (редактируемый) и `ues.py` (хардкод) — две разные системы. Оценки считаются по хардкоду.
- Нет блокирующих критериев (красные флаги не отсекают вакансии).
- Нет проверки опыта, английского, формата работы как Gate.

**Что чинить (в порядке приоритета):**
1. Подключить `matrix.yaml` к UESCalculator (заменить `kw_map` на чтение YAML)
2. Добавить в YAML секцию `blocks` с блокирующими критериями (режим `reject`)
3. Gate A и Gate B сделать параметризуемыми из конфига, а не хардкода
4. Добавить проверку опыта (experience_years) и английского (english_level)
5. Написать автотест: те же 10 вакансий → те же результаты

**Что НЕ нужно:**
- Никакого хардкода. Любое правило = конфиг (YAML). matrix.yaml = единственный источник истины.
- Универсальность: matrix.yaml должен работать для любого пользователя, не только для текущего профиля.
